# Call Center Insights 📞

> **SIMULATED DATA WARNING**: All evaluation and demo audio recordings and transcripts bundled or generated by this project are **strictly simulated and synthetic**. No real customer recordings or real personal data are ever committed, stored, or processed.

A local-first pipeline for analyzing call-center audio recordings. It extracts per-call and aggregate operational metrics: customer sentiment at start vs end, representative performance quality, issue resolution status, and resolution time in minutes.

---

## Architecture

```text
       +-----------------------+
       | Call Audio (.wav/.mp3)|  (Stereo: L=Agent, R=Customer; or Mono)
       +-----------+-----------+
                   |
                   v
       +-----------------------+
       |   faster-whisper STT  |  Configurable model (tiny / base / small)
       | (transcribe.py)       |  Stereo channel separation or mono inferred
       +-----------+-----------+
                   |
                   v
       +-----------------------+
       |     PII Redaction     |  Regex + Luhn card validation
       | (redact.py)           |  Redacts emails, cards, SSNs, phones, digits
       +-----------+-----------+  *Before saving or sending to any model*
                   |
                   v
       +-----------------------+
       | LLM Extraction Engine |  Pydantic v2 validation + retry on invalid JSON
       | (extract.py)          |  Providers: baseline (offline), ollama, anthropic
       +-----------+-----------+
                   |
                   +---> Grounding Check: verifies quotes exist verbatim in transcript
                   |
                   v
       +-----------------------+
       |   Timing Analytics    |  Resolution time = (quote timestamp - 1st cust seg)
       | (timing.py)           |  Purely deterministic math; never guessed or hallucinated
       +-----------+-----------+
                   |
                   +-----------------------------+
                   v                             v
       +-----------------------+    +-----------------------+
       | Reports & CSV Export  |    | Streamlit Dashboard   |
       | (report.py / cli.py)  |    | (app.py)              |
       +-----------------------+    +-----------------------+
```

## Why Emotion Labels Come From Transcript Text Only (Not Prosody)

In `callinsight`, acoustic features extracted via `librosa` (`prosody.py`: pitch mean/std, RMS energy, speaking rate) are **strictly descriptive** and are **never used to feed or alter sentiment/emotion labels**.

**Why?**
1. **Hardware & Acoustic Confounders**: Microphone frequency responses, compression codecs (e.g. 8kHz G.711 telephony), gain levels, and background ambient noise artificially inflate pitch and energy variance.
2. **Cultural & Demographic Bias**: Pitch baseline and speaking cadence differ naturally across gender, age, native language, and regional accents. Treating higher pitch or faster speech as "angry" introduces severe systematic bias into call-center evaluations.
3. **Auditing & Grounding**: Categorical sentiment labels must be explainable and verifiable against verbatim text evidence. Prosody is retained solely as descriptive telemetry for human reviewers.

---

## Privacy & Legal Considerations

- **Recording Consent Laws**: Audio recording consent laws vary significantly across jurisdictions (e.g., "one-party consent" vs "two-party / all-party consent" states in the US, GDPR in Europe). Ensure proper legal disclosures ("This call may be recorded for quality assurance") before capturing any real audio.
- **Redaction Scope and Limits**: The redaction engine removes emails, phone numbers, credit/debit card numbers verified via the Luhn checksum, SSN patterns, and long digit strings. **Personal names are NOT reliably removed by regex patterns**, as contextual NER models on informal spoken transcripts frequently misclassify common nouns or miss uncommon names. Do not treat regex redaction as a complete de-identification guarantee.

## Quick Start

### 1. Installation

Requires Python 3.11.

```bash
# Clone and enter directory
cd call-center-insights

# Create and activate virtual environment
python3.11 -m venv .venv
source .venv/bin/activate

# Install dependencies and editable package
pip install --upgrade pip
pip install -r requirements.txt
pip install -e .
```

### 2. Run Test Suite

```bash
pytest -v
```

### 3. Generate Simulated Demo Audio

Renders 10 simulated stereo recordings using local macOS `say` and `ffmpeg` (Left channel = Agent Samantha, Right channel = Customer Daniel):

```bash
python -m evals.render_audio --limit 10 --out samples/
```

### 4. Analyze Audio Recordings via CLI

```bash
python -m callinsight.cli analyze samples/ --out reports/ --whisper base
```

Output files produced in `reports/`:
- `reports/calls_report.csv`: Per-call data with sentiment shift, resolution, grounding, and evidence quotes.
- `reports/summary_report.json`: Aggregate metrics (resolution rate, avg resolution time, etc.).
- `reports/summary_report.md`: Markdown summary.

### 5. Launch the Streamlit Dashboard

```bash
streamlit run app.py
```
Open `http://localhost:8501` to view interactive KPI cards, sentiment shift charts, and drill down into individual calls with timestamped evidence quotes.

## Evaluation Benchmark & Provider Comparison

The project includes 40 hand-crafted, simulated call transcripts with ground-truth labels across both standard interactions and deliberate edge cases:
- *polite but unresolved* (customer remains courteous, but request is denied)
- *resolved but still angry* (issue fixed, but customer remains angry at company)
- *sarcasm* ("What a brilliant update to wipe my server!")
- *interruptions* (rapid speaker turn-taking)
- *thanks with no fix* (customer says "thanks anyway" without resolution)
- *escalation to supervisor*
- *customer calms down* (angry start -> handled well -> satisfied end)

Split:
- **Dev Set (20 calls)**: Used for initial measurement and quality gating.
- **Test Set (20 calls)**: Held-out test set written before evaluation; never tuned against.

### Baseline Failure Modes (Why Weak Baselines Fail)
1. **Sarcasm Blindness**: VADER scored sarcastic praise ("Oh fantastic, what a masterpiece of software design to wipe my data") as positive compound sentiment, predicting *satisfied* when the true sentiment was *angry*.
2. **Polite False-Resolutions**: When customers politely said "thank you so much for checking anyway" after a denied refund or coupon, keyword rules detected "thank you" and falsely classified the call as *resolved*.
3. **Escalations**: Complex multi-turn conflicts without explicit resolution keywords default to *unclear* rather than identifying that the customer was transferred or remained unresolved.

### Running Quality Gate Command

```bash
python -m evals.run_eval \
  --provider baseline \
  --split dev \
  --no-audio \
  --min-sentiment-start-acc 45.0 \
  --min-sentiment-end-acc 50.0 \
  --min-resolution-acc 60.0 \
  --min-grounding-rate 95.0 \
  --max-resolution-time-mae 0.50
```
Exits `0` if all thresholds pass; exits `1` if any threshold is violated.

## Limitations

1. **Simulated Data Only**: The evaluation datasets and demo audio are synthetic and TTS-generated. Real call centers have overlapping crosstalk, acoustic clipping, background chatter, and telephony codecs.
2. **Small Benchmark Sample**: 40 calls provide meaningful regression detection for hard conversational cases, but a production system requires hundreds of calls across distinct customer service domains.
3. **Transcript-Based Emotion**: Because prosody is descriptive only, subtle emotional cues (tone of voice, deadpan delivery, quiet sobbing) are not captured if not reflected in the transcript words.
4. **Mono Speaker Diarization**: When processing mono audio without stereo channel separation, speaker attribution confidence is halved (0.50) and marked as inferred, as local Whisper does not perform native diarization.
5. **Whisper Transcription Errors**: Automatic speech recognition struggles with heavy accents, specialized domain jargon (e.g. medical codes, hardware part numbers), and low-bitrate telephony (25.09% WER measured on TTS samples).
